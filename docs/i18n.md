# Translations

The interface exists in English and German. **English is the default and the fallback** — it is what a
reader gets when their language has no value for a key.

Both artifacts read the same shape of file: flat JSON, one key per line, no nesting. **The files are the
source** — they are written by hand and reviewed like code; nothing generates them.

| | Backend (`core/`) | Dashboard (`dashboard/`) |
|---|---|---|
| Files | `src/main/resources/messages/{en,de}.json` | `src/assets/i18n/{en,de}.json` |
| Read by | `JsonMessageSource`, a Spring `MessageSource` | ngx-translate |
| Placeholders | `{0}`, `{1}` (`MessageFormat`) | `{{name}}` |
| Used for | notification texts, error messages | everything a person sees |

## Adding a string

1. Pick a key: flat, `{feature}.{sub}.{element}` — `matrix.cell.movingTag`, `component.field.tagPattern`.
   `nav.*` for navigation labels, `error.*` for error messages, `notification.*` for the daily message.
2. Add it to **every** file of the artifact, at its place in alphabetical order, with a text in every
   language. A string used by both artifacts goes into the files of both.
3. Use it in the code — the `translate` pipe in a template, `TranslationService` in the backend.

Removing a string works the same way backwards: out of the code, out of every file.

**Writing the texts:**

- German addresses the reader formally — `Sie`, `Ihr`, `Ihnen`, never `du`, not even on a button.
- Domain terms stay technical and untranslated: tag, digest, registry, SemVer, EOL, patch, minor, major,
  rollback, snooze, prerelease. Translated, they make the tool harder to use, not easier.
- Placeholders are the same in every language: a German text that drops `{0}` hides the value.

## Verifying

```bash
./gradlew :core:verifyTranslations    # backend: the files among themselves
./gradlew :core:verifyMessageKeys     # backend: the files against the code
cd dashboard && npm run i18n:verify   # dashboard: both
```

**Among themselves**, every file of an artifact carries every key, each with a text and the same
placeholders, one key per line in alphabetical order. The order keeps the files line by line side by
side, so a review sees a missing text at a glance, and it turns a key written twice into an error — JSON
keeps the second one and drops the first without a word.

**Against the code**, every key the code asks for exists, and every key in the files is asked for
somewhere. The first direction closes the gap that shows up on screen: ngx-translate renders a missing
key as the key itself, and the backend hands it to whoever reads the message — nothing else reports it.
The second finds texts left behind by removed code.

Keys built at runtime are resolved rather than skipped: `"taskSection." + section.name()` is expanded over
the constants of that enum, and `'constraintState.' + check.state` over the members of the TypeScript
union of the same name. A prefix with no such type behind it is an error, not a pass. A key handed around
before it is translated — returned from a method, say — counts as used once it is written as a literal
in the code.

All three run in the pipeline: the backend checks hang off `./gradlew check`, the dashboard check runs
before the build.

## Why the files are flat

The dots belong to the key; they are not a path. The backend's `JsonMessageSource` reads the top level of
a file and nothing below it, so a nested file resolves nothing there — the build stays green and only the
messages are empty. The dashboard keeps the same shape, so one rule holds for every file, and the checks
refuse a nested file in both.
